🚨 Задача Fraud Detection
Обнаружение мошеннических транзакций в реальном времени при жёстких ограничениях: <50мс, 99.9% uptime, класс 0.1% мошенников.

Fraud Detection — одна из немногих задач где ошибки имеют прямую денежную стоимость с обеих сторон: пропустить фрод = потеря денег клиента. Заблокировать легитимную транзакцию = потеря клиента + репутационный ущерб.

💸
False Negative (пропустили фрод)

Мошеннические транзакции прошли. Прямые потери. Visa/MC chargeback — банк платит. $28.6B потери от card fraud в мире (2020, Nilson Report)

Легитимная транзакция отклонена. Клиент звонит в поддержку или уходит к конкурентам. 30% людей отказываются от карты после 1 ложной блокировки.

Главная особенность: задача не симметричная. Стоимость FN и FP принципиально разная. Нельзя оптимизировать accuracy — нужен аккуратный подбор threshold с учётом бизнес-стоимости ошибок.
⚖️ Precision–Recall Tradeoff
Центральная дилемма fraud detection: чем строже фильтр, тем больше легитимных транзакций блокируем.
Confusion Matrix для Fraud Detection
TN — Легитимный → ✅
98,900
FP — Легитимный → ❌
100
FN — Фрод → ✅
10
TP — Фрод → ❌
90

Precision = TP/(TP+FP) = 90/(90+100) = 47%

Recall = TP/(TP+FN) = 90/(90+10) = 90%

F1 = 2×P×R/(P+R) = 2×0.47×0.90/1.37 = 61.9%

Accuracy = (TN+TP)/(all) = 98990/99100 = 99.9% — бесполезная метрика!

Accuracy 99.9% достигается предсказанием "всё легально" — но Recall=0! Для fraud detection: ключевые метрики Recall (ловим мошенников), Precision (не беспокоим честных), PR-AUC.
F-beta Score — балансировка Precision и Recall
$$F_\beta = (1+\beta^2) \cdot \frac{\text{Precision} \cdot \text{Recall}}{\beta^2 \cdot \text{Precision} + \text{Recall}}$$
$\beta = 1$: равный вес (F1-score).
$\beta = 2$: Recall важнее в 2 раза — когда пропустить фрод хуже чем заблокировать честного. Типично для банков и Stripe.
$\beta = 0.5$: Precision важнее — когда FP дорог (VIP-клиенты, большие суммы).
🤏 Почему PR-AUC лучше ROC-AUC при дисбалансе классов

ROC-AUC: ось X = FPR = FP/(FP+TN). При миллионах легитимных транзакций даже 1000 FP даёт очень маленький FPR → ROC кривая выглядит "хорошо" даже при плохом качестве.

PR-AUC: ось X = Recall, ось Y = Precision. Не учитывает TN → более честная оценка при дисбалансе. 0.1% fraud → random baseline PR-AUC = 0.001. Модель с PR-AUC = 0.8 — хорошая.

Правило: при доле позитивного класса <5% → смотри PR-AUC и Average Precision, а не ROC-AUC.

🔢 Как выбрать threshold: cost-based оптимизация
Дано
Стоимость FN (пропустили фрод): $50 средняя потеря. Стоимость FP (заблокировали честного): $5 (обработка звонка + риск ухода клиента).
Цель
Минимизировать $\text{Cost} = 50 \times FN + 5 \times FP$.
Расчёт
Для каждого threshold τ вычисляем FN(τ) и FP(τ) по validation set → выбираем τ* = argmin Cost(τ). При tau=0.3: FP=200, FN=5 → Cost = 250+1000=1,250$. При tau=0.5: FP=50, FN=20 → Cost = 250+100=350$. Оптимум: tau≈0.5!
Для сегментов
Разные threshold для разных сегментов: VIP-клиенты → высокий threshold (не беспокоим). Новые пользователи → низкий threshold (подозрительнее).

Focal Loss — формула
$$\text{FL}(p_t) = -\alpha_t (1-p_t)^\gamma \log(p_t)$$
$p_t$ — предсказанная вероятность правильного класса. $\gamma \geq 0$ — focusing parameter. $\alpha_t$ — балансировочный вес (обратно пропорционален частоте класса).
При $\gamma=0$: стандартный cross-entropy. При $\gamma=2$: легко классифицируемые примеры (p_t=0.9 → фактор (0.1)²=0.01) почти не влияют на loss → модель фокусируется на трудных примерах (фрод похожий на легитимные операции).
🤏 Focal Loss — зачем нужен

Стандартная cross-entropy: 99.9% примеров — легитимные транзакции. Loss = −log(0.999) ≈ 0.001 для каждой из 999 легитимных → суммарный градиент от них огромный. 1 fraud-пример: loss = −log(0.01) ≈ 4.6 → но их 1000 меньше.

Результат: модель игнорирует редкий класс. Focal Loss: для легитимной с p=0.999 → вес (1-0.999)² = 0.000001. Практически вычеркиваем простые примеры! Модель учится на сложных маргинальных случаях.

⚡ Velocity Features
Самые информативные признаки для fraud — подозрительное поведение во времени: "3 транзакции за 1 минуту", "5 разных стран за час".

Velocity features = агрегаты по скользящему временному окну. Мошенник спешит: он должен использовать украденные данные пока карта не заблокирована → много транзакций за короткое время в новых местах.

Velocity Feature Formulas
$$v_{k,w}(u,t) = \sum_{t'=t-w}^{t-1} \mathbb{1}[\text{entity}(t')=k]$$ $$\text{или}\quad v_{k,w}^{\text{sum}}(u,t) = \sum_{t'=t-w}^{t-1} \text{amount}(t') \cdot \mathbb{1}[\text{entity}(t')=k]$$
Velocity = count/sum событий по entity $k$ (карта, пользователь, устройство, IP) в окне $[t-w, t)$.
Ключевые velocity признаки:
  • card_txn_count_1h — количество транзакций по карте за последний час
  • card_txn_amt_sum_24h — суммарная сумма транзакций по карте за сутки
  • user_countries_distinct_6h — количество уникальных стран за 6 часов
  • ip_fraud_rate_30d — историческая доля фрода с данного IP за 30 дней
  • device_new_card_count_7d — сколько разных карт использовалось с устройства за неделю
🤏 Почему velocity важнее статических признаков

Статические признаки: страна карты, тип мерчанта, сумма. Мошенник знает эти паттерны и имитирует их. "Транзакция из России на Amazon за $50 — выглядит нормально".

Velocity: "5 транзакций за 3 минуты в 3 часах ночи, 3 разных страны, 2 разных мерчанта" — это поведенческий профиль, который сложно имитировать. Velocity features дают 60-70% SHAP importance в production-моделях Stripe.

🔢 Типичная Feature Store архитектура (Stripe-like)
Offline
Warehouse (S3 / BigQuery): исторические транзакции → Spark job → предвычисленные признаки → Parquet files → Training dataset.
Online
Stream (Kafka → Flink): входящие транзакции → real-time aggregation → Redis (TTL 7 дней). Каждый ключ: card:12345:txn_count_1h → 3.
Bridge
Point-in-time join: при обучении — каждой транзакции в train set соответствуют feature values на момент t. Не используем "будущие" значения velocity!
Feature catalog
Метаданные о каждом признаке: owner, description, SLA, data lineage. "card_txn_count_1h: ответственный — team fraud, SLA 99.9% uptime, max latency 2ms".
🔄 Concept Drift в Fraud Detection
Мошенники адаптируются. Паттерны фрода 2023 года ≠ паттерны 2024. Модель без обновлений деградирует.

Fraud detection — классический пример adversarial concept drift: мошенники активно изучают систему и адаптируют атаки. После каждого крупного блокирования схемы → новая схема.

Data drift

PSI
Population Stability Index
Population Stability Index (PSI) — детектор дрифта
$$\text{PSI} = \sum_{i=1}^{k} (E_i - A_i) \cdot \ln\!\left(\frac{E_i}{A_i}\right)$$
$E_i$ — доля наблюдений в бакете $i$ в reference (обучающий период). $A_i$ — доля в текущем периоде.
PSI < 0.1: стабильно. PSI 0.1–0.2: небольшой сдвиг, мониторинг. PSI > 0.2: значительный дрейф → ретрейн!
Вычисляется по каждому признаку отдельно → находим "дрейфующие" признаки → понимаем какая схема фрода меняется.
🤏 PSI — интуиция через пример

Признак: сумма транзакции. В обучающих данных: 70% транзакций 1-100$, 20% 100-500$, 10% 500$+.

Через 6 месяцев: 40% 1-100$, 30% 100-500$, 30% 500$+. PSI = (0.70-0.40)×ln(0.70/0.40) + (0.20-0.30)×ln(0.20/0.30) + (0.10-0.30)×ln(0.10/0.30) ≈ 0.18+0.04+0.22 = 0.44. PSI > 0.2 → РЕТРЕЙН ОБЯЗАТЕЛЕН.

Что произошло: инфляция + рост онлайн-покупок → средний чек вырос. Модель не знает о новых крупных транзакциях — может их неправильно классифицировать.

🔢 Стратегии работы с concept drift
Trigger-based
Мониторим PSI / метрики на daily validation set. При PSI > 0.2 или Precision/Recall просадка > 5% → автоматический триггер ретрейна. Stripe: модель обновляется каждые 2-4 недели.
Window-based
Скользящее окно данных для обучения: всегда последние 90 дней. Старые паттерны вытесняются свежими. Риск: потеряем редкие но устойчивые схемы фрода.
Weighted
Экспоненциальное убывание веса старых данных: $w_t = e^{-\lambda(T-t)}$. Последние данные важнее без резкого отсечения истории. $\lambda$ = гиперпараметр скорости забывания.
Online Learning
Обновляем модель каждую транзакцию или каждый час. Логистическая регрессия / SGD — обновляются инкрементально. Проблема: нужна быстрая разметка (label). Для фрода: chargeback приходит через 30-90 дней!

🕸️ Graph ML для Fraud Detection
Мошеннические сети: скоординированные атаки через связанные аккаунты. Graph features дают +10-20% к качеству.

Ключевые инсайты: мошенники создают синтетические сети аккаунтов (synthetic identity fraud). Аккаунты используют общие устройства, IP, email домены, телефоны. Граф раскрывает эти связи.

Graph Features для транзакции (u, v, t)
Node features (карта / мерчант):
  • Degree: количество связанных сущностей (карт связанных с IP, IP связанных с устройством)
  • Fraud rate: доля прошлых фрод-транзакций узла
  • Clustering coefficient: насколько "клика" соседей связана между собой
  • PageRank: мера "подозрительности" в сети связей
Edge features (связь):
  • shared_device_count: сколько карт использовали то же устройство
  • shared_ip_fraud_rate: доля фрода от карт с этого IP
  • bipartite_link_strength: сила связи карта-мерчант через количество транзакций
Реализация: NetworkX (small graphs), DGL/PyG (Graph Neural Networks), Spark GraphX (large scale).
🔢 Пример: synthetic identity fraud через граф
Сеть
Мошенник создал 50 карт. Все они регистрировались с 3 IP-адресов. 15 карт использовали 2 устройства. Граф: IP → Card → Device → Merchant.
Граф-признак
ip_shared_cards_count = 50/3 ≈ 17. Легитимный пользователь обычно: 1-2 карты с одного IP. 17 карт с одного IP → аномально высокий connected component.
GNN
GraphSAGE или GAT обучается агрегировать представления соседей. Новая карта получает embedding = функция(собственных признаков, признаков соседних карт). Даже без истории — заражается "репутацией" сети.
Результат
PayPal: добавление graph features к LGBM дало +18% AUC на synthetic identity fraud. Стандартная модель без графа: AUC 0.82. С графом: AUC 0.97.

💳 Stripe · Fraud Detection (Engineering Blog, 2023)

Как Stripe обрабатывает $640B платежей в год с точностью >99%

  • Radar Rules Engine: до ML — 200+ детерминированных правил (block_if: country='XX' AND amount>1000). Обрабатывает 10-15% транзакций немедленно без ML.
  • ML Score: LightGBM с 500+ признаками. Обучается каждые 2 недели на последних 90 днях. Velocity features через Kafka→Redis pipeline.
  • Ensemble: несколько моделей для разных типов фрода: card testing (маленькие проверочные транзакции), ATO (account takeover), synthetic identity. Финальный score = weighted ensemble.
  • 3DS Step-up: при score 0.3-0.7 → отправить на 3D Secure вместо блокировки. Балансирует UX и безопасность.
  • Latency: p50=12ms, p99=45ms. SLA = 50ms. Выполняется за счёт pre-computed features в Redis и ONNX inference.

Ключевые технические решения Stripe:

❓ Q&A — 12 вопросов
▶Почему accuracy — плохая метрика для fraud detection? популярный
При 0.1% fraud rate: модель "всегда говорит легитимная" имеет accuracy 99.9% — но ловит 0% мошенников!

Правильные метрики:
- Recall (Sensitivity): доля пойманного фрода. Максимизируем.
- Precision: доля реального фрода среди заблокированных. Минимум FP.
- F-beta score: баланс, обычно с β=2 (Recall вдвое важнее).
- PR-AUC: площадь под Precision-Recall кривой. Более честна при дисбалансе чем ROC-AUC.
- Business metrics: потери от фрода ($) + потери от FP ($) — конечная метрика оценки.
▶Что такое velocity features и почему они важны? популярный
Velocity features = агрегаты поведения за скользящее временное окно.

Примеры:
- card_txn_count_1h: количество транзакций по карте за час
- card_amt_sum_24h: суммарная сумма за сутки
- user_countries_distinct_6h: уникальные страны за 6 часов
- ip_fraud_rate_30d: исторический % фрода с этого IP

Почему важны: мошенник спешит (карту скоро заблокируют) → аномально высокая активность за короткое время. Статические признаки можно имитировать, поведение во времени — сложнее.

В production-моделях velocity features занимают 60-70% SHAP importance.
▶Как организовать real-time inference с latency <50ms? практика
Архитектурные решения:

1. Pre-compute features: velocity features вычисляются непрерывно (Kafka→Flink→Redis). При запросе — только lookup, не вычисление.
2. In-memory Feature Store: Redis или Aerospike. Latency p99 <2ms. TTL на старые данные.
3. ONNX/PMML inference: LightGBM конвертируется в ONNX. Inference на CPU ≈5ms. Не нужен Python runtime.
4. Rule Engine первым: детерминированные правила (<1ms) фильтруют ~15-20% случаев без ML.
5. Async updates: обновление velocity counters — асинхронно после ответа клиенту.

SLA decomposition: network 5ms + feature lookup 2ms + real-time features 2ms + inference 8ms + decision 1ms + buffer = ~25ms p50, 45ms p99.
▶Что такое concept drift и как его мониторить? deep dive
Concept drift = изменение статистической зависимости P(Y|X) во времени. В fraud: мошенники меняют тактику → старая модель хуже ловит новые схемы.

Типы дрифта:
- Sudden drift: новая схема фрода появляется резко (массовый phishing attack)
- Gradual drift: постепенное изменение (инфляция меняет distribution сумм)
- Adversarial drift: мошенники специально имитируют легитимные транзакции

Мониторинг:
- PSI по каждому признаку: PSI > 0.2 → ретрейн
- Performance drift: Recall на rolling validation window. Снижение >5% → alarm
- Feature distribution shift: KL-divergence или Kolmogorov-Smirnov тест
- Chargeback rate trend: рост chargebacks → модель пропускает новый тип фрода
▶Как бороться с дисбалансом классов в fraud? практика
Порядок предпочтения на практике:

1. scale_pos_weight = neg/pos в LightGBM: вес fraud-класса = 99900/100 = 999. Быстро, без изменения данных, хорошо работает.
2. class_weight='balanced' в sklearn LogisticRegression/SVC
3. Focal Loss в нейросетях: γ=2 подавляет лёгкие примеры
4. SMOTE или ADASYN для синтетических примеров: помогает при очень малых классах (<0.01%)
5. Threshold optimization: оптимизировать threshold по бизнес-метрике (cost matrix), не 0.5

Не рекомендую: random oversampling + undersampling вместе — приводит к переобучению на синтетических данных.
▶Как Feature Store решает проблему train-serve skew? популярный
Train-serve skew: при обучении признаки вычислены одним способом, при инференсе — другим. Результат: offline метрики хорошие, production — плохие.

Feature Store решение:
1. Единое определение признака: "card_txn_count_1h = count транзакций card_id за последний час до транзакции t (exclusive)". Одна реализация, два использования.
2. Point-in-time correct training: при генерации train set — для каждой строки берём feature values на момент timestamp транзакции из исторического хранилища.
3. Online serving: те же feature definitions, но из live Redis.

Популярные open-source: Feast, Hopsworks, Tecton. AWS: SageMaker Feature Store. GCP: Vertex AI Feature Store.
▶Что такое card testing fraud и как его детектировать? deep dive
Card testing: мошенник получил список украденных карт. Проверяет каждую маленькой транзакцией (0.01$, 1$) на легитимном мерчанте. Если прошла → использует для крупных покупок.

Характерные паттерны:
- Очень маленькие суммы (outlier amount_percentile)
- Высокая частота с одного IP/device (velocity!)
- Новые карты без истории
- Специфические мерчанты (парковки, donation sites — низкий порог)

Detection signals:
- ip_txn_count_1h > 10 → подозрительно
- device_unique_cards_24h > 5 → очень подозрительно
- amount < 2$ AND is_new_card → flag
- merchant_card_testing_rate — исторический % card testing через этого мерчанта
▶Как использовать граф-признаки для fraud? deep dive
Граф строится из сущностей: карты, IP-адреса, устройства, email, телефоны, мерчанты.

Рёбра: "карта X использовалась с IP Y", "IP Y также использовался карта Z", etc.

Простые граф-признаки (без GNN):
- degree(IP) = сколько карт использовали этот IP
- fraud_rate(device) = доля фрода транзакций с этого устройства
- shared_device_with_fraud_account: связан ли пользователь через устройство с известным фродером

GNN подход (PayPal, JPMorgan):
GraphSAGE/GAT: каждый узел = embedding = функция(собственных признаков, агрегат признаков соседей). Новый узел "заражается" репутацией соседей.

Результат: +10-20% AUC на synthetic identity fraud vs модель без графа.
▶Как выставить правильный threshold? практика
Не используйте 0.5 по умолчанию! При дисбалансе 0.1% оптимальный threshold обычно 0.1-0.3.

Метод 1: Cost-based оптимизация
Для каждого threshold τ: Cost(τ) = cost_FN × FN(τ) + cost_FP × FP(τ). Выбираем τ* = argmin Cost.

Метод 2: F-beta максимизация
Максимизируем F₂ (если Recall важнее) на validation set по grid τ = [0.01, 0.02, ..., 0.99].

Метод 3: Precision@K
Устанавливаем фиксированное число ручных проверок в день (K). Threshold = K-й percentile скоров.

Метод 4: Multi-threshold
Разные threshold для разных сегментов: VIP-клиенты (высокий threshold), новые пользователи (низкий), транзакции в ночное время (средний).
▶Что такое 3DS и как ML решает когда его использовать? популярный
3D Secure (3DS) = дополнительная аутентификация: SMS, push-уведомление, биометрия. Перекладывает ответственность на эмитента → chargeback платит банк, не мерчант.

Проблема: 3DS фрикция → часть пользователей бросает покупку (abandonment rate 15-30%). Нельзя применять ко всем.

ML-решение (Stripe, Adyen):
- Низкий fraud score (0-0.3): approve без 3DS
- Средний (0.3-0.7): step-up → 3DS
- Высокий (>0.7): block немедленно

Результат: оптимальный "step-up" использует 3DS только для 5-10% транзакций, ловя 80-90% фрода с минимальной фрикцией для честных клиентов.
▶Как оценить ROI от улучшения fraud модели? практика
Формула ROI:
ΔRevenue = ΔRecall × fraud_volume × avg_fraud_amount
ΔCost_FP = ΔFPR × legit_volume × cost_per_FP
Net benefit = ΔRevenue − ΔCost_FP

Пример:
Recall: 85% → 90% (+5%). Fraud volume: $10M/год. avg fraud: $500.
ΔRecall = 5% → дополнительно поймали 0.05 × 10M/500 = 1,000 транзакций → $500K сохранили.

FPR: 0.5% → 0.6% (+0.1%). Legit volume: $1B. Cost per FP: $5.
ΔFP = 0.001 × $1B/avg_legit($200) = 5,000 доп. блокировок. Cost = 5,000 × $5 = $25K.

Net benefit = $500K − $25K = $475K/год от улучшения Recall на 5%.
▶Как обрабатывать delayed labels в fraud detection? deep dive
Проблема: chargeback (подтверждение фрода) приходит через 30-90 дней после транзакции. Для онлайн-обучения нужна немедленная метка.

Решения:
1. Proxy labels: использовать быстрые сигналы — пользователь позвонил в поддержку через 24ч, карта заблокирована через 48ч. Не идеальны но быстры.
2. Batch retrain: переобучаем с реальными chargeback метками каждые 2-4 недели. Принятое решение в большинстве production-систем.
3. Positive-unlabeled (PU) learning: знаем что часть "легитимных" (unlabeled) на самом деле фрод (еще не received chargeback). PU learning учитывает это при обучении.
4. Active learning: отправлять подозрительные транзакции (score 0.4-0.7) на ручной review → быстрая разметка от аналитиков → онлайн обновление.
