Свойства векторного пространства
$$\text{Арифметика:}\quad \vec{v}_{\text{король}} - \vec{v}_{\text{мужчина}} + \vec{v}_{\text{женщина}} \approx \vec{v}_{\text{королева}}$$ $$\text{Кластеризация:}\quad \text{столицы близко друг к другу},\;\text{страны близко друг к другу}$$
Знаменитый пример Word2Vec: "король − мужчина + женщина = королева". Это не запрограммировано вручную — модель сама выучила эти аналогии из текстов. Такие "аналогические рассуждения" — главное доказательство, что эмбеддинги учат смысл.
🤏 На пальцах — арифметика векторов

Аналогия с GPS-координатами: Москва − Россия + Франция ≈ Париж. "Столица Франции" = "столица" + "Франция". Вектор "столица" = Москва − Россия (разница сохраняется). Прибавляем Франция → получаем Париж.

Слова, стоящие в похожих контекстах, имеют похожие векторы. "Кошка ест рыбу" и "собака ест мясо" — в похожих контекстах → кошка и собака близко.

📖 Word2Vec
Google, 2013 (Mikolov et al.). Два архитектурных варианта: CBOW и Skip-gram. Фундамент современных NLP-эмбеддингов.

Идея: обучить нейросеть предсказывать контекст по слову (Skip-gram) или слово по контексту (CBOW). Побочный эффект — обученные веса скрытого слоя = отличные эмбеддинги.

CBOW (Continuous Bag of Words)

Контекст → центральное слово. Быстрее, хуже для редких слов.

["кошка","ест","..."] — контекст
↓ avg/sum
Скрытый слой (d=128) — ЭТО И ЕСТЬ ЭМБЕДДИНГ
↓ softmax
"рыбу" — предсказываем центральное слово

Skip-gram

Центральное слово → контекст. Лучше для редких слов.

"ест" — центральное слово
↓ embedding lookup
Скрытый слой (d=128) — ЭТО И ЕСТЬ ЭМБЕДДИНГ
↓ softmax (×|V| вычислений)
["кошка","рыбу"] — предсказываем контекст
Skip-gram Objective (Negative Sampling)
$$\mathcal{L} = -\log\sigma(\vec{v}_{w_O}^T \vec{v}_{w_I}) - \sum_{k=1}^{K}\mathbb{E}_{w_k\sim P_n}\!\left[\log\sigma(-\vec{v}_{w_k}^T \vec{v}_{w_I})\right]$$
$\vec{v}_{w_I}$ — вектор центрального слова. $\vec{v}_{w_O}$ — вектор слова-контекста. $\sigma$ — сигмоида. K — число негативных примеров (обычно 5–20).
Вместо softmax по всему словарю (100K+ операций) — binary classification: "это настоящий контекст" vs "это случайное слово". Даёт ускорение в ~100x.
🤏 Negative Sampling — зачем и как

Проблема: обычный softmax требует вычислить вероятность для каждого из 100K слов словаря — на каждый шаг обучения. Слишком медленно.

Решение: превращаем в бинарную задачу. Берём пару (кошка, ест) → это "позитив" (метка=1). Берём K случайных слов: (кошка, стул), (кошка, удар) → "негативы" (метка=0). Учим бинарный классификатор: реальный контекст или нет? K=5 негативов → 1+5=6 операций вместо 100K.

Отрицательные слова берутся из распределения $P_n(w) \propto U(w)^{3/4}$ — чуть убираем перевес частотных слов.

GloVe — альтернатива (Stanford, 2014)
$$J = \sum_{i,j=1}^{V} f(X_{ij})\!\left(\vec{w}_i^T\tilde{\vec{w}}_j + b_i + \tilde{b}_j - \log X_{ij}\right)^2$$
$X_{ij}$ — число совместных вхождений слов i и j в окне. GloVe строит матрицу совместной встречаемости (матрица X) и факторизует её логарифм. Отличие от Word2Vec: Word2Vec — предиктивная (sliding window), GloVe — подсчётная (global co-occurrence matrix). На практике качество сопоставимо.
🤏 Word2Vec vs GloVe — когда что

Word2Vec: хорош для больших корпусов (интернет, соцсети), онлайн-обучение, можно дообучивать инкрементально.

GloVe: хорош для небольших корпусов где важна глобальная статистика совместной встречаемости. Предобученные GloVe-векторы (Wikipedia) часто хороший baseline.

Сейчас оба вытесняются контекстуальными эмбеддингами (BERT, GPT) — там одно слово имеет разные векторы в разных контекстах.

⏰ Когда использовать Word2Vec
  • Domain-specific корпус: медицинские тексты, юридические документы, код — предобученные на Wikipedia не подойдут
  • Классификация / поиск похожих документов: average word vectors = sentence embedding (быстро, неплохо)
  • Feature engineering для RecSys: пользователь просмотрел seq=[a,b,c,d] → обучаем как "предложения" → item2vec
  • Не подходит: задачи где важен контекст (одно слово = разные значения) → BERT
🛒 Item2Vec
Word2Vec для товаров/контента. Ключевая идея: сессии покупок = "предложения", товары = "слова".

Идея: если в одной сессии куплены [iPhone, AirPods, Чехол], значит они "встречаются в одном контексте" — как слова в предложении. Обучаем Word2Vec на сессиях → получаем item embeddings.

⏰ Когда Item2Vec лучше обычного CF
  • Cold start для нового товара: если у него нет взаимодействий, но он похож на известный по тексту/категории → можно взять эмбеддинг похожего
  • "Похожие товары": ANN-поиск по эмбеддингам — быстро и хорошо. Яндекс.Маркет, Wildberries используют именно это
  • Feature для downstream модели: эмбеддинги товара как входной признак в LightGBM-ранкере

Matrix Factorization — суть
$$R \approx P \cdot Q^T$$ $$\hat{r}_{ui} = \vec{p}_u \cdot \vec{q}_i = \sum_{k=1}^{K} p_{uk} \cdot q_{ik}$$
$R$ — матрица U×I (users × items). $P$ — матрица U×K (user latent factors). $Q$ — матрица I×K (item latent factors). K — число скрытых факторов (обычно 32–512).
Число параметров: (U+I)×K vs U×I. При U=1M, I=1M, K=128: 2M×128 = 256M vs 1T (в 4000 раз меньше!).

Loss function с регуляризацией
$$\mathcal{L} = \sum_{(u,i)\in\mathcal{K}}\!\left(r_{ui} - \vec{p}_u \cdot \vec{q}_i\right)^2 + \lambda\!\left(\|\vec{p}_u\|^2 + \|\vec{q}_i\|^2\right)$$
Суммируем только по наблюдаемым парам $\mathcal{K}$ (не по всем ?). Регуляризация $\lambda$ предотвращает overfitting. Оптимизируем: SGD или ALS. При неявной обратной связи (clicks, views) — используют WALS (Weighted ALS) или BPR (Bayesian Personalized Ranking).
🤏 Что значат скрытые факторы K

Представь K=2: фактор 1 = "жанр" (экшн←→драма), фактор 2 = "сложность" (простой←→глубокий).

Алиса: p_u = [0.9, 0.2] — любит экшн, не любит сложное.
Кино A: q_i = [0.9, 0.1] — боевик, простой.
Прогноз: 0.9×0.9 + 0.2×0.1 = 0.81+0.02 = 0.83 → Алиса должна понравиться ✅

На практике K=128–512 и факторы не интерпретируются вручную — модель сама открывает нужные измерения.

⚙️ ALS — Alternating Least Squares
Основной алгоритм обучения MF для больших данных. Используют Netflix, Spotify, Apple Music.
ALS — Алгоритм
$$\text{Шаг 1: фиксируем Q, оптимизируем P:}\quad \vec{p}_u = \left(Q^T Q + \lambda I\right)^{-1} Q^T \vec{r}_u$$ $$\text{Шаг 2: фиксируем P, оптимизируем Q:}\quad \vec{q}_i = \left(P^T P + \lambda I\right)^{-1} P^T \vec{r}_i$$
ALS чередует шаги: фиксируем одну матрицу, решаем аналитически для другой. Каждый шаг — закрытая форма (аналитическое решение)! Сходится к локальному минимуму. Параллелизируется идеально: каждый пользователь/item независим. Apache Spark MLlib ALS — стандарт для больших данных.
🤏 Почему ALS, а не SGD

SGD: обновляем по одной паре (u,i) за раз. Трудно параллелить — если обновляем user_1, то нельзя одновременно обновлять item_1 (зависимость). Хорош для online learning.

ALS: фиксируем Q → все пользователи независимы → параллелим на 1000 воркеров. Следующий шаг: фиксируем P → все items независимы. Чередуем. Идеален для Spark/Hadoop. Netflix использовал именно ALS для своей CF-системы.

🔢 Пример ALS — 2 пользователя, 3 фильма, K=1

Начальные значения (случайные): P=[0.5, 0.3]ᵀ, Q=[0.4, 0.6, 0.5]ᵀ, λ=0.1

Матрица оценок R (только наблюдаемые): r₁₁=5, r₁₂=4, r₂₂=2, r₂₃=4

1
Шаг 1 — фиксируем Q=[0.4, 0.6, 0.5], обновляем p₁:
$p_1 = \frac{q_1\cdot r_{11} + q_2\cdot r_{12}}{q_1^2 + q_2^2 + \lambda} = \frac{0.4\times5 + 0.6\times4}{0.4^2+0.6^2+0.1} = \frac{2.0+2.4}{0.16+0.36+0.1} = \frac{4.4}{0.62} = \mathbf{7.1}$
2
Обновляем p₂ (видел только фильмы 2 и 3):
$p_2 = \frac{q_2\cdot r_{22} + q_3\cdot r_{23}}{q_2^2+q_3^2+\lambda} = \frac{0.6\times2+0.5\times4}{0.36+0.25+0.1} = \frac{1.2+2.0}{0.71} = \frac{3.2}{0.71} = \mathbf{4.5}$
3
Шаг 2 — фиксируем P=[7.1, 4.5], обновляем q₁ (только r₁₁=5):
$q_1 = \frac{p_1\cdot r_{11}}{p_1^2+\lambda} = \frac{7.1\times5}{7.1^2+0.1} = \frac{35.5}{50.5} = \mathbf{0.70}$
4
Прогноз для Влада (p₂=4.5) для Кино 1 (q₁=0.70):
$\hat{r}_{2,1} = p_2 \times q_1 = 4.5 \times 0.70 = \mathbf{3.15}$
Прогноз Алисы (p₁=7.1): $7.1 \times 0.70 = 5.0$ (оценила высоко ✅)

🏷️ Entity Embeddings для табличных данных
Guo & Berkhahn, 2016 — Rossmann Store Sales competition. Вместо one-hot — обучаемые эмбеддинги категориальных признаков.
Entity Embedding Layer
$$\vec{e}_{x} = E[\text{category\_id}], \quad E \in \mathbb{R}^{|\mathcal{C}| \times d}$$ $$d = \min\left(50, \left\lceil\frac{|\mathcal{C}|}{2}\right\rceil\right) \quad \text{(правило Fastai)}$$
$E$ — матрица эмбеддингов, обучается совместно с основной задачей (регрессия, классификация). $|\mathcal{C}|$ — мощность категории. Для "магазин" с 1000 магазинами → вектор размером min(50, 500) = 50 (вместо one-hot 1000). Обучаемые эмбеддинги учат семантику категорий из таргета.
🤏 Почему лучше one-hot

One-hot кодирование "магазин 1": [1,0,0,...,0]. Магазин 1 и магазин 2 одинаково "далеко" друг от друга и от магазина 999. Нет понятия "похожие магазины".

Entity embedding: магазин в Москве, ТЦ, высокий трафик → вектор [0.8, 0.2, 0.9, 0.1]. Другой московский ТЦ → [0.7, 0.3, 0.8, 0.2]. Модель выучила "московские ТЦ" как кластер. Полезно для прогнозирования продаж: магазины с похожими паттернами дают похожие прогнозы.

Результат: на Rossmann конкурсе (Kaggle, 2015) entity embeddings улучшили качество на ~10% vs XGBoost с one-hot.

📏 Меры сходства в эмбеддинговом пространстве
Как сравнивать векторы — cosine, dot product, Euclidean. Каждая имеет своё применение.
Cosine Similarity
$$\cos(\vec{u}, \vec{v}) = \frac{\vec{u} \cdot \vec{v}}{\|\vec{u}\|\|\vec{v}\|} = \frac{\sum_k u_k v_k}{\sqrt{\sum_k u_k^2}\cdot\sqrt{\sum_k v_k^2}}$$
Диапазон: [−1, 1]. Инвариантен к масштабу вектора — измеряет только угол, не длину. Идеален для семантического сходства слов/документов.
🤏 На пальцах — cosine

"кошка" = [1, 0] (только первый фактор). "котёнок" = [0.9, 0.1]. "громко" = [0, 1] (только второй фактор).

cos(кошка, котёнок) = (1×0.9+0×0.1)/(1×√(0.82)) = 0.9/0.91 = 0.99 — очень похожи.
cos(кошка, громко) = (1×0+0×1)/(1×1) = 0.0 — не похожи.

Dot Product Similarity
$$\text{score}(\vec{u}, \vec{v}) = \vec{u} \cdot \vec{v} = \sum_k u_k v_k$$
Зависит от длины векторов — популярные items (длинные векторы) будут ранжироваться выше. Именно это используется в MF: $\hat{r}_{ui} = \vec{p}_u \cdot \vec{q}_i$. Также в Two-Tower моделях для ANN-поиска (fast inner product search — FAISS, ScaNN).
Euclidean Distance
$$d(\vec{u}, \vec{v}) = \|\vec{u} - \vec{v}\|_2 = \sqrt{\sum_k (u_k - v_k)^2}$$
Обратно пропорционально сходству. Подходит когда важна абсолютная величина (не только направление). Например, в k-NN поиске по эмбеддингам. Чувствителен к масштабу — требует L2-нормализации перед применением.

🎵 Spotify · Music2Vec и Podcast Embeddings

Как Spotify строит embeddings для 100M+ треков

Collaborative filtering: 500M+ пользователей × 100M+ треков — классический ALS не масштабируется. Решение: matrix factorization через implicit feedback (количество прослушиваний, пропусков).

  • Track2Vec: playlist sessions как "предложения" (аналог Item2Vec). Треки в одном плейлисте → обучаем Word2Vec → получаем audio embeddings без анализа звука.
  • Content + CF fusion: audio features (tempo, key, loudness) + CF embeddings → combined representation для холодного старта новых треков.
  • Serving: 100M+ векторов → FAISS (Facebook AI Similarity Search) для ANN-поиска соседей за <10ms.
  • Результат: "Discover Weekly" (100M+ пользователей, выходит каждый понедельник) — целиком на embeddings-based CF.

Ключевые решения Spotify:
1. Implicit feedback weighting: полное прослушивание = weight 1.0, 50% прослушивание = 0.5, пропуск = 0.1. WALS с этими весами лучше чем бинарный liked/disliked.
2. Two-Tower для Discover Weekly: User Tower (история, явные предпочтения) + Track Tower (audio, metadata) → cosine similarity → top-K candidates → re-ranking. Two-tower позволяет предвычислить track embeddings оффлайн, а user vector — в реальном времени.
3. Temporal decay: прослушивания давнего прошлого имеют меньший вес ($w_t = w \times e^{-\alpha(T-t)}$). Музыкальные вкусы меняются — старые взаимодействия менее релевантны.
🏠 Airbnb · Listing & User Embeddings (KDD 2018)

Real-Time Personalization с embeddings (знаменитый Paper)

Задача: как обучить embeddings для 5.5M listings (квартир) и 400M пользователей, которые отражают предпочтения по стилю, локации, ценовому диапазону?

  • Session-based: последовательность кликов пользователя за сессию = "предложение". Клик на квартиру = "слово". Забронированная квартира = специальный глобальный контекст (всегда позитивный сигнал).
  • Negative sampling: случайные листинги из той же геолокации (не со всего мира) — это "hard negatives", которые делают модель лучше различать похожие квартиры в одном районе.
  • User type embeddings: для cold start пользователя — маппинг на "тип пользователя" (страна, устройство, язык) → тип имеет embedding.

📺 YouTube · Two-Tower RecSys (2019)

Двухбашенная архитектура для 1B+ видео

Проблема: нельзя в online вычислить similarity(user, video) для 1B видео. Решение: разделить на offline index-building + online user-tower.

  • Item Tower (offline): вычисляет embedding для каждого из 1B+ видео. Обновляется раз в часы/дни. Индексируется в ScaNN (ANN-поиск).
  • User Tower (online): вычисляет embedding пользователя из его истории просмотров в реальном времени. За <10ms.
  • Retrieval: ANN-поиск top-500 кандидатов. Затем более тяжёлый ранкер (ranking model) для финального top-10.

❓ Q&A — 10 вопросов
▶Что такое эмбеддинг и чем он лучше one-hot? популярный
Эмбеддинг — плотный числовой вектор фиксированного размера, представляющий объект (слово, товар, пользователя) в непрерывном пространстве.

Преимущества над one-hot:
1. Размерность: 100K слов → one-hot 100K-dim. Embedding → 128-dim. Сжатие в 780 раз.
2. Семантика: похожие объекты → похожие векторы. One-hot: все объекты одинаково "далеко" (расстояние √2).
3. Непрерывность: можно интерполировать, находить соседей, выполнять арифметику.
4. Обобщение: объекты с похожими векторами получают похожие предсказания → лучше generalize.
▶Как выбрать размер d для эмбеддингов? практика
Правило Fastai: $d = \min(50, \lceil|C|/2\rceil)$ — для категориальных эмбеддингов.

Общие рекомендации:
- Word embeddings: 50–300 (небольшие задачи), 512–1024 (BERT-style)
- RecSys (ALS): 32–256 в зависимости от объёма данных
- Сущности в prod: 32–128 (баланс качество/скорость)

Практика: начинать с d=64, валидировать на hold-out. Если Recall@10 растёт при d=128 — увеличивать. Plateau = оптимальный d.

Осторожно: большой d → больше памяти (1M items × 512 = 2GB float32), медленнее ANN-поиск.
▶В чём разница между ALS и SGD для Matrix Factorization? сравнение
ALS (Alternating Least Squares):
- Аналитическое решение на каждом шаге
- Идеально параллелится (независимые пользователи/items)
- Хорошо для batch, распределённые системы (Spark)
- Медленнее сходится при больших K

SGD (Stochastic Gradient Descent):
- Стохастическое обновление по одной паре
- Трудно параллелить (Hogwild — асинхронный SGD)
- Хорош для online learning (новые данные потоком)
- Быстрее на GPU при больших K

Вывод: корпоративные системы на Spark → ALS. Deep learning + нейросети → SGD/Adam.
▶Что такое cold start и как embeddings помогают его решить? популярный
Cold start — проблема отсутствия данных для нового пользователя или нового товара.

Решения через embeddings:

Для нового товара (item cold start):
- Content-based embedding: из описания (BERT), картинки (ResNet), категории (entity emb)
- "Похожий товар": найти ANN-соседей среди известных items → взять их CF-embedding
- Airbnb: listing2vec использует geographic и property features для инициализации

Для нового пользователя:
- User type embedding: маппинг (страна, устройство, возраст) → тип → embedding типа
- После первых N взаимодействий → переключиться на personalized embedding
▶Как устроен FAISS и когда его использовать? deep dive
FAISS (Facebook AI Similarity Search) — библиотека для эффективного поиска ближайших соседей в высокомерных пространствах.

Ключевые алгоритмы:
- IVF (Inverted File Index): кластеризует пространство → при запросе проверяем только ближайшие кластеры. k-means на GPU.
- HNSW (Hierarchical Navigable Small World): граф навигации. Быстрее IVF, больше памяти. Spotify использует HNSW.
- PQ (Product Quantization): сжимает векторы 10-50x → помещается в RAM. Небольшая потеря точности.

Когда использовать:
- >1M векторов → нельзя brute force
- Latency требование <100ms для top-K запроса

Альтернативы: ScaNN (Google, 2x быстрее FAISS), Annoy (Spotify), hnswlib.
▶Чем Two-Tower отличается от обычного MF? популярный
Matrix Factorization: User embedding + Item embedding + dot product. Обучается только на взаимодействиях (clicks, ratings). Не использует content features напрямую.

Two-Tower (Neural CF):
- User Tower и Item Tower — нейросети любой сложности
- Входы: произвольные features (текст, изображения, числа, история)
- Выход: фиксированного размера dense вектор из обоих башен
- Score = dot product или cosine двух векторов

Преимущества Two-Tower перед MF:
1. Может использовать богатые features (не только ID)
2. Лучший cold start (через content features в башнях)
3. Нелинейные взаимодействия внутри каждой башни

Компромисс: сложнее обучать, дольше inference (если башни тяжёлые).
▶Что такое контекстуальные эмбеддинги и чем они лучше Word2Vec? deep dive
Word2Vec — статический эмбеддинг: слово "банк" всегда имеет один вектор. Не различает "банк финансовый" и "берег реки".

Контекстуальные (BERT, GPT): вектор слова зависит от окружающего контекста. "Банк" в "Центральный банк снизил ставку" и "Банк реки был крутым" → разные векторы.

Почему лучше:
- Полисемия (многозначность) обрабатывается корректно
- Учёт длинных зависимостей (attention span = весь документ)
- State-of-the-art на большинстве NLP-задач

Почему Word2Vec всё ещё используют:
- В 100x быстрее при training и inference
- Для RecSys (item sequences) — BERT излишен
- Лёгкий деплой (3MB vs 400MB BERT)
▶Как оценить качество эмбеддингов? практика
Intrinsic evaluation (прямая оценка):
- Аналогии: король − мужчина + женщина = ? (Word Analogy Task). Accuracy on word analogy datasets.
- Similarity: косинусное сходство пар слов vs человеческая оценка (WordSim353, SimLex999)
- Визуализация: t-SNE / UMAP → семантически похожие объекты кластеризуются?

Extrinsic evaluation (через downstream task):
- Recall@K при рекомендациях (ItemCF → hit rate по K позициям)
- NDCG@K — ранжирование
- Accuracy/F1 классификатора на downstream задаче

На практике: intrinsic — быстрая проверка. Extrinsic — настоящий критерий качества.
▶Что такое BPR (Bayesian Personalized Ranking)? deep dive
BPR — objective для implicit feedback (нет оценок, только клики/просмотры). Основная идея: просмотренный item должен ранжироваться выше непросмотренного для данного пользователя.

$$\mathcal{L}_{BPR} = -\sum_{(u,i,j)\in D_S}\ln\sigma(\hat{r}_{ui} - \hat{r}_{uj})$$
Где $(u, i, j)$ — пользователь $u$, позитивный item $i$ (просматривал), негативный item $j$ (не просматривал).

Зачем вместо MSE: MSE пытается предсказать "реальный рейтинг" — но при implicit feedback нет реальных оценок. BPR оптимизирует порядок (ranking) — именно то, что нужно для RecSys.
▶Как работает ANN-поиск (Approximate Nearest Neighbors)? популярный
Проблема точного поиска: найти ближайший вектор среди 100M → нужно 100M вычислений distance. Слишком медленно для <100ms latency.

ANN — приблизительный поиск: пропускаем часть пространства, ищем только в "перспективных" регионах. Теряем ~1-5% точности, выигрываем в скорости в 100-1000x.

Алгоритмы:
- LSH (Locality Sensitive Hashing): хешируем векторы так, чтобы близкие векторы попали в один бакет.
- IVF (Inverted File): k-means кластеризация → при запросе ищем в top-N кластерах.
- HNSW: многоуровневый граф. Быстрый навигационный поиск. Recall~99%.

Практика: FAISS (Meta) → Spotify, Facebook. ScaNN (Google) → YouTube. Annoy (Spotify) — для умеренных данных.
